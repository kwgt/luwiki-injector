# 手動復旧

## 1. 復旧の進め方

投入は複数ページのtransactionではありません。先行成功は残り、最初の失敗や安全停止で
後続は未実行になります。`overwrite` は削除後の再作成で、元ページを自動復元しません。
再実行は現在状態とmodeに応じた新しい操作です。無条件に安全な続きからの再開ではありません。

1. stdoutのReportとstderrの警告・診断から、確定事実と未確認事項を整理します。
2. 元入力の版、root付き入力参照、対象path、旧/既知新IDを照合します。
3. 対象Wikiの現在状態を確認する方法と、その観測・操作による作用を確認します。
4. 対象・mode・権限・他者変更・残存物への影響を判断し、必要な操作だけを明示的に選びます。

この文書は判断手順を説明します。既存page/history/soft-delete/draft/lockの解除・削除・復元、
新たな投入を包括して許可するものではありません。管理者と対象・作用を確認してから行います。
実本文や秘密値を復旧メモ・共有ログへ貼らず、本文比較は権限のある場所で行ってください。
modeと終了コードは [利用手順](USAGE.md)、保証範囲は
[上限と検証範囲](LIMITS_AND_VALIDATION.md) を参照してください。

## 2. Reportから読み取ること

| 情報 | 読み方 |
| --- | --- |
| ページ別結果 | 成功、同一skip、警告付き適用、失敗、未実行を区別。失敗/未実行だけから未適用とは断定しない |
| pathと入力参照 | `root/a.md` は元入力、`/取込先/a` は投影先。prefixとroot除去を取り違えない |
| 旧ID・revision | 事前に確認した旧ページの識別情報。現在も同じとは仮定しない |
| 既知の新ID | 作成応答等で確定した新ページの識別情報。応答喪失時に推測して補わない |
| 原因段階と最後の試行段階 | 最初に失敗した原因と、再照合/cleanup等の最後の試行を分ける |
| 主・補助・cleanup | 主原因、再照合等の補助失敗、停止時処理の結果を分ける。cleanup試行がHTTP送信を証明するとは限らない |
| 警告 | 目的状態を観測しても異常応答等の警告は残る。後続失敗でも先行警告は消えない |
| 削除・lock観測 | 削除確認なしは存在確認ではなく未確認。lock観測なしも解放済みと解釈しない |

例えば旧ページ削除確認と新IDがある場合も、「旧削除」「新ページの存在」「新本文適用」
「lockの所有と使用可能性」は別々の事実です。旧leaseと新ページのleaseを混ぜません。
Reportの確定事実、別主体の事後観測、その観測時点をそれぞれ記録してください。
返っていないID、削除状態、lock状態、元runの欠けた完了時刻を補完しないでください。

## 3. 先行成功と後続未実行

例：`root/a.md` は成功、`root/b.md` は失敗、`root/c.md` は未実行。
CLIが確定した先行成功は自動で戻りません。bの失敗が応答不明ならbの適用有無は未確認です。
cの未実行はその実行で後続処理へ進まなかったことを示し、別主体による変更の不存在は示しません。

現在のa/b/cのpathとIDを確認し、失敗原因と元入力の版を確認します。
同じ全入力を `error` で再実行すると、成功済みaの存在で停止し得ます。
`update`/`overwrite` は同一ならskipですが、相違なら更新/削除再作成を行います。
先行ページが他者によって変更されていれば、その内容への影響も判断してください。
対象を絞る場合も必須rootや親ページ非生成、入力安全検査を維持し、
必要な入力とmodeを利用者が明示して再実行します。製品による自動resumeはありません。

## 4. POST応答喪失とID不明

draft作成POSTの応答を失うと、サーバーで作成済みでもCLIがIDを確定できない場合があります。
この場合は停止し、自動でPOSTを再送しません。既知新IDがないことは未作成の証明ではありません。

まず対象path、実行時刻、サーバー側で利用可能な履歴/状態を管理者と確認します。
path照会の結果だけで、不明なdraftの不存在やlock解放を断定しないでください。
IDが不明なまま再投入すると、既存/draftとの衝突や重複した操作を招く可能性があります。
metadata照会の副作用も第9節で確認します。
作成済みか不明なままなら未知として保留し、確定していないIDへの解除・削除を行いません。
確認できた状態と新規作成の影響を判断してから、利用者が明示的に次の操作を選びます。

## 5. PUTの目的状態確認済みと未確認

PUTが500・通信断等になっても、サーバーで本文適用済みの可能性があります。
同じ期限・取消境界が許す場合、CLIは同ID/current/期待path/目的bytesを単回再照合します。
新規/updateの目的状態が確認できれば警告付き適用を報告しますが、異常を正常成功へ置き換えず
非0で終了します。再作成PUTでは目的状態確認後も独立した安全停止理由が残る場合があります。

確認済みなら、その観測時点での目的状態を記録し、警告・後続未実行・終了理由を読みます。
確認に失敗した場合、期限等で照合できなかった場合は適用有無を未知として残します。
現在のID/path/revisionと必要な本文の一致を権限のある場所で確認し、
他者変更を含む現状に対して再投入が必要か判断します。
同じPUTを「前回失敗したから」と自動再送する手順はありません。

## 6. 旧削除済み・再作成失敗・新draft残存

`overwrite` は相違する旧ページを削除してから新ページを作成します。
旧削除後に新POSTや本文PUTが失敗すると、旧ページがsoft-deleteのまま残り、
新draftやlockが残る場合があります。新IDが分かるか、本文適用済みかも個別に確認します。

旧ID/旧revision/削除確認と、新ID/新本文/新lockの情報を分けて記録してください。
DELETE完全500の後は旧削除とpath不存在を確認できた時だけ規定経路で再作成に進みます。
通信状態不明や不正成功から削除を推測して再作成範囲を広げることはありません。
POST以降が不確定なら停止します。

旧ページの自動復元、新draftの自動回収、旧lock tokenの再利用はありません。
draftのunlockは削除を伴い得るため、「lockだけ解除する」つもりで実行しないでください。
旧履歴を保存したまま何を現在ページにするか、他者のdraftではないか、
必要権限と復元/削除/再投入の影響を管理者と確認して明示操作を選びます。

## 7. 期限後に本文が適用された場合

取得からWiki操作まで同じ絶対期限・取消を使います。
到達後は再照合、自分が保持する既存lockの解除を含め追加HTTPを発行しません。
別の後処理猶予はありません。ただし、既に進行中だった変更がサーバー側で
期限後に適用される可能性は残ります。

実期限の観測ではCLI Reportが3 Created/1 Failed/3未実行で、
別主体の事後観測では4本文の適用が確認されました。
「期限後追加HTTP0」と「適用3件だけ」は同じ命題ではありません。
CLIの確定情報と事後観測を時点付きで分け、進行中だったページの現在状態を確認します。
期限切れを理由に即座に全件再投入せず、適用/lock不明を残したまま推測で処置しません。

## 8. 他者競合とlock不明

事前確認後に本文やIDが変わる、lock取得/延長が失敗する等の場合は停止します。
更新時はロック後に本文を再取得し、overwriteは削除直前にIDと本文を再照合します。
他者変更を前提の古い入力で上書きする許可へ読み替えないでください。

現在のpath/ID/revisionと変更主体を確認し、対象内容と実行時刻を関係者と調整します。
remoteがlockedと見えるだけでは、自分の使用可能なlockを保持している証拠になりません。
延長が不確定、新headerが不正等の場合に旧tokenを再使用可能へ戻しません。
lock期限はRFC3339で扱い、不正/受信時期限切れなら停止し、時計ずれ補正や猶予を設けません。
所有や使用可能性が不明なlockを解除せず、管理者と状態/作用を確認して判断します。

## 9. 観測と手動操作の作用

LuWiki 0.9.32のmetadata照会にも期限切れlock/draftのcleanup作用があり得ます。
「GETだから状態を変えない」と仮定せず、対象ID/pathと観測による作用を確認してください。
Bearerのpath prefix制約はID指定にも適用され、既知IDでも権限の免除はありません。
lock解除はdraft削除になり得ます。取得したlockという事実だけから非draftとは断定できません。

製品が停止時に自動解放するのは、非draft・保持確実・同client/ID・使用可能性と共有境界を
満たす既存leaseに限られます。draftを自動unlock/回収しません。
手動操作も対象の所有・現在状態・削除作用を確認し、他者のlockや履歴を推測で変更しません。
ログ・メモには本文、認証値、Authorization、Git資格情報、lock tokenを残さず、
確定したID/path/revision/入力参照/処理段階だけで共有できる記録を作ります。
